# EduAtlas / ScholarPilot AI — Comprehensive Project Audit

**Audit date:** 22 November 2026  
**Audit target:** repository working tree at the time of review  
**Overall conclusion:** feature-rich prototype; **not production-ready for broad enrollment or sensitive student-data processing**

## Scope and assurance

The review covered the repository’s first-party Python services and API, FastAPI routing and middleware, frontend JavaScript/CSS/HTML templates, data-model and JSON-store implementation, tests, documentation, dependency manifests, GitHub workflows, Render configuration, Docker configuration, and tracked data-file shapes. Repository inventory included the tracked files and pre-existing untracked application files. Third-party `node_modules`, Git internals, generated bytecode, and binary artwork were not reviewed line-by-line. Personal record values were deliberately not copied into this report.

This is a static repository audit, not a penetration test, legal/privacy assessment, live-provider check, or load test. External scholarship claims and live production settings were not independently verified. The worktree already contained numerous modified and untracked files before this audit; those changes were preserved. This report is a new deliverable and does not imply those pre-existing edits were made as part of the audit.

**Post-audit remediation:** At the user's request, the two HIGH findings in this report and the reCAPTCHA fail-open finding (Finding 3) were addressed in the current worktree. Advisor cache entries are now scoped to a trusted account identity and anonymous requests do not use personalized response caches; a regression test was added. Mutable runtime JSON files were removed from the Git index while preserving local working files, and Git/Docker ignore rules now exclude them and uploaded media. For reCAPTCHA, `verify_recaptcha()` now strictly fails closed in production, rejecting protected requests when `RECAPTCHA_SECRET_KEY` is missing or contains a placeholder; test token bypass is strictly disabled in production and kept only in development/testing; startup environment validation checks `RECAPTCHA_SECRET_KEY`; Render config was updated to require `RECAPTCHA_SECRET_KEY` and set `ENVIRONMENT: production`; and automated tests in `tests/test_recaptcha_security.py` cover all production and development scenarios. The exposed records remain in Git history until a separately planned history cleanup; token/credential rotation and production image replacement are still operational follow-ups.

Validation performed:

- Python `compileall` for `services`, `web`, and `dispatch_weekly_subscribers.py`: **passed**.
- `npm.cmd run lint`: **failed**, reporting 37 errors and 5 warnings, predominantly browser globals treated as undefined.
- `npm.cmd run typecheck`: **failed**, with many JavaScript type-checking errors (including missing global declarations and implicit-any diagnostics).
- `npm.cmd run audit`: **passed**, reporting zero known npm vulnerabilities in the lockfile at audit time. The Node dependencies are development-only.
- `python -m pytest -q`: **not runnable** because `pytest` is unavailable.
- Installing `requirements-dev.txt` was attempted; package resolution failed for SQLAlchemy in the available package index. Consequently, the Python test suite and a Python dependency audit could not be completed.

## 1. Executive summary

EduAtlas combines scholarship discovery and matching, student profiles, a Gemini-backed advisor, application-document assistance, email/Telegram notifications, news, and a student community. Its target users are students seeking international scholarships, with the current content and defaults particularly oriented toward Palestinian applicants. There is no evidenced payment, subscription, or institutional-sales implementation in this repository; the business model is therefore **undetermined**, not implemented.

The codebase has meaningful breadth and several useful foundations: FastAPI, Pydantic, SQLAlchemy/PostgreSQL support, password hashing, session/CSRF utilities, security headers, email verification, and a substantial UI. However, the production-readiness claims in some repository documents overstate what the deployment and validation evidence supports. In particular:

1. Tracked runtime JSON includes student account and subscriber records with authentication/profile fields. The Docker build copies the repository wholesale, and `.dockerignore` does not exclude runtime data or uploaded media.
2. The advisor’s semantic response-cache check is not actually scoped to a user: cached entries do not store the `user_scope` field that the lookup expects. Similar queries may receive another user’s personalized cached advice.
3. Scholarship content is hard-coded as “verified” while containing deadlines that had already passed on the audit date. It is also used as a fallback, so stale content can be presented as current.
4. Persistence can fall back to local JSON. This is unsafe for concurrent writes, horizontal scaling, and durable production data.
5. Scheduled work, rate limiting, caches, and telemetry are process-local. Replicas can duplicate work and do not share enforcement or state.
6. The primary API module is a roughly 3,900-line monolith; schema setup/migration is partly implicit at startup; automated checks are not green and Python tests could not run here.

**Decision:** treat the current application as an internal pilot/demo. The two selected HIGH findings have been mitigated in the current worktree, but history cleanup and credential rotation remain necessary. Before onboarding more real students, verify every scholarship source/deadline and make production persistence and scheduled work durable and multi-instance-safe.

## 2. Project discovery

### Project overview

EduAtlas is an academic-opportunity navigation product intended to reduce the effort of finding scholarships and preparing applications. It is more than a static portal: the repository implements student identity/profile management, a scholarship catalog and matching flow, advisor/chat and document-review routes, notification preferences and delivery, news, and community interactions.

**Primary users:** international scholarship seekers and applicants.  
**Secondary users implied by features:** scholarship administrators/content operators, student-community moderators, and newsletter subscribers. No operational institutional/partner console or organization tenancy was established by this code review.

### Data flow (textual)

1. A student browses the catalog or supplies profile criteria.
2. The application loads scholarships from SQLAlchemy/PostgreSQL or JSON fallback and combines them with curated/external search results.
3. Matching and advisor code uses profile, criteria, catalog entries, and sometimes conversation history to produce results. Gemini is called for some tasks; deterministic/rule-based responses and a hard-coded curated fallback also exist.
4. Account/profile, community, news, and notification mutations are persisted through the database service or JSON files.
5. Background/cron tasks discover or process opportunities, match subscribers, and send email/Telegram/in-app notifications.

The report did not find an implemented source-ingestion approval lifecycle (source identity, captured evidence, reviewer, verified-at time, expiry, and change history) sufficient to substantiate the product’s “verified/real-time” claims.

### User journey analysis

1. **Discovery:** anonymous visitor lands on the public homepage, views radar/news/community, or uses public catalog/search surfaces.
2. **Registration:** student submits account/profile details, receives a verification email/code, then establishes a session.
3. **Personalization:** student fills in country, degree, GPA, majors, language, and preferences.
4. **Action:** student sees ranked opportunities, saves them, asks the advisor, reviews documents, and receives reminders.
5. **Engagement:** student returns via email/Telegram, reads news, and participates in the community.

The journey’s strongest value is moving from discovery to application readiness. Its weakest point is trust: a student may act on a wrong deadline or an apparently precise “chance” that is not calibrated to historical admissions outcomes. The first-run path should make eligibility, evidence, freshness, and uncertainty explicit before recommending action.

### Maturity and readiness

- **Maturity:** feature-rich prototype / early pilot, not a proven production platform.
- **MVP readiness:** **not ready for broad public MVP** until the P0/P1 risks below are resolved and the test suite runs in CI. A limited demo using synthetic data is reasonable.
- **Scalability readiness:** **low**. There is no measured load capacity, durable distributed job layer, multi-instance data-safety guarantee, or operational SLO evidence.

## 3. Security audit

The security review covered authentication/session handling, authorization and ownership checks, request validation, CSRF/CORS/headers, uploads, AI context/cache behavior, secrets/configuration, persistence, and deployment artifacts. Findings below are evidence-backed and focus on reachable risk. No destructive exploit steps or payloads are included.

### Security summary table

| # | Severity | File | Lines | Vulnerability | Confidence |
|---|----------|------|-------|---------------|------------|
| 1 | 🟠 HIGH | `services/advisor_service.py` | 2658-2659, 2758-2769 | Semantic advisor cache can serve personalized responses across users because cached entries omit the user scope checked by the reader. | 10/10 |
| 2 | 🟠 HIGH | `data/users.json`, `data/subscribers.json`, `.dockerignore`, `Dockerfile` | `users.json` 1-668; `subscribers.json` 1-247; `.dockerignore` 1-9; `Dockerfile` 22-25 | Sensitive runtime records are tracked and are copied into Docker build context/image along with local uploads. | 9/10 |
| 3 | 🟡 MEDIUM | `services/security_utils.py`, `render.yaml` | `security_utils.py` 1518-1528; `render.yaml` 30-33 | CAPTCHA verification succeeds when the production secret is absent or placeholder, and Render does not configure the secret. | 9/10 |
| 4 | 🟢 RESOLVED | `web/app.py`, `web/dependencies.py` | 114-135, 580-625 | Cron secret accepted in query parameters. Resolved: query params removed, X-Cron-Secret header enforced. | 10/10 |

### Finding 1 — Cross-user personalized AI response cache

- **Severity:** High.
- **Impact:** A student can receive another student’s profile-aware advisor answer. If the generated response contains personal or academic information, this becomes cross-account disclosure; even when it does not, recommendations can be incorrectly personalized.
- **Affected files:** `services/advisor_service.py`.
- **Evidence:** The semantic lookup reads `entry.get("user_scope")` and only filters a different user when that field is present (around lines 2658-2659). The cache writer builds `cache_data` without a `user_scope` property (around lines 2758 onward), then puts it into the shared module-level cache (lines 2767-2769). Therefore `entry_user` is absent and the intended cross-user guard is bypassed for these entries.
- **High-level scenario:** One student asks a question that produces a personalized answer; another student asks a sufficiently similar question while the entry is cached and may receive that answer.
- **Exact fix:** Store a normalized, non-PII user identifier in each cached entry and require an exact scope match during every semantic lookup; reject entries with missing scope rather than treating them as shared. Prefer cache keys that include user/profile version and scholarship ID. Add a regression test with two distinct profiles and similar prompts.

### Finding 2 — Student/runtime data in source control and container build

- **Severity:** High; potentially Critical if the repository or built image is available to untrusted parties.
- **Impact:** Exposure of student identity/profile records and authentication-related fields; distribution of local uploads and runtime data in deployment artifacts; retention in Git history persists after deleting a working-tree file.
- **Affected files:** `data/users.json`, `data/subscribers.json`, other runtime `data/*.json`, `.gitignore`, `.dockerignore`, `Dockerfile`.
- **Evidence:** Git tracks `data/users.json` and `data/subscribers.json`; the current files contain account/subscriber records and fields including email, password hash, verification/reset fields, and profile attributes. `.gitignore` does not exclude runtime JSON stores. `.dockerignore` excludes only a small set of development paths and does not exclude `data/` or `web/static/uploads/`. `Dockerfile` uses `COPY --chown=user:user . .` and then makes `data` and upload directories part of the image.
- **High-level scenario:** Anyone with repository access can inspect committed records; anyone with access to a published image can retrieve files copied into that image. Deleted records may remain in Git history or prior images.
- **Exact fix:** Stop tracking all live records and local uploads; use synthetic fixtures only. Rotate/revoke credentials, sessions, tokens, and reset/verification material as applicable; assume historical values persist until history/artifact cleanup is verified. Purge exposed records from Git history and old images where policy permits. Change the Docker build to an allowlist of source files and add explicit ignores for runtime stores, `.env`, secrets, uploads, scratch data, and local artifacts. Store uploads in private object storage.

### Finding 3 — CAPTCHA verification fails open in production (Remediated)

- **Severity:** Medium.
- **Impact:** Registration and public forms can lose their intended bot-abuse barrier, increasing automated account creation, spam, and provider cost.
- **Affected files:** `services/security_utils.py`, `render.yaml`, `web/app.py`, `.env.example`, `tests/test_recaptcha_security.py`.
- **Evidence:** `verify_recaptcha()` treats an absent or placeholder secret as a successful bypass (lines 1518-1528); Render configuration does not provision `RECAPTCHA_SECRET_KEY` (lines 30-33).
- **High-level scenario:** Requests that reach a CAPTCHA-protected workflow can be accepted without a provider-verified challenge when the production secret is unset.
- **Exact fix:** Require a valid production CAPTCHA secret and fail closed for protected actions. Keep any bypass/test-token behavior behind an explicit test-only setting that cannot be enabled in production. Add a startup configuration check and an integration test proving missing production configuration rejects the action.
- **Remediation status:** Remediated. `verify_recaptcha()` now verifies `is_production_environment()` and fails closed if `RECAPTCHA_SECRET_KEY` is missing or contains placeholder values. Test tokens are strictly rejected in production. Dev bypass is preserved for development/testing environments only. `validate_environment_at_startup()` and `validate_production_configuration()` validate reCAPTCHA keys at startup. `render.yaml` was updated with `ENVIRONMENT: production` and `RECAPTCHA_SECRET_KEY`. Full test coverage added in `tests/test_recaptcha_security.py`.

### Finding 4 — Cron credential accepted in query strings [RESOLVED]

- **Severity:** Medium (Remediated).
- **Impact:** A logged or copied request URL can disclose the cron credential, allowing unauthorized triggering of protected automation while the credential remains valid.
- **Affected files:** `web/app.py`, `web/dependencies.py`.
- **Evidence:** `require_cron_auth()` previously accepted `secret` and `cron_secret` query parameters in addition to the `X-Cron-Secret` header; the scan route also exposed a query `secret` parameter.
- **Remediation Status:** ✅ **Fixed & Verified**.
  - Query parameters `secret` and `cron_secret` removed from all endpoint signatures and auth extractors.
  - Schedulers and cron callers must provide credentials strictly via the `X-Cron-Secret` HTTP header.
  - Any request containing `secret` or `cron_secret` query parameters is immediately rejected with HTTP 403 Forbidden.
  - Automated tests added in `tests/test_critical_security_fixes.py` and `tests/test_production_hardening.py` confirming query parameter authentication is rejected.

### Other security controls and areas

- The code contains password-hashing/session utilities, CSRF middleware, security-header middleware, request validation models, and cron-secret checks. These are positive foundations but do not neutralize the findings above.
- The CAPTCHA fail-open path and URL-based cron secret are additional verified weaknesses; configure CAPTCHA as a required production dependency and keep credentials out of URLs.
- The repository includes an older `SECURITY_AUDIT.md` and claims in `SECURITY.md`; treat these as documentation, not evidence that every described control is correctly wired or currently enforced. Reconcile documentation after remediation.
- Static review cannot establish whether secrets were previously exposed in Git history, whether production environment values are safe, or whether the live deployment has additional controls. Perform a history/secret scan and production configuration review before launch.
- The delegated static security review reported no additional exploitable findings in SQL/NoSQL injection, SSRF, unsafe upload, or authorization/IDOR beyond the four findings above. This is not a guarantee of absence: the review did not test a live deployment, production configuration, or every runtime state, so those areas still require regression tests and pre-launch verification.

|---|---|---|---|

## 5. Architecture review

### Strengths

- Domain intent is visible in separate service modules for auth, scholarships, AI advisor, search, automation, email, notifications, community, and news.
- API routes and frontend surfaces cover the core journey rather than only a landing page.
- PostgreSQL/Neon support and an ORM exist; this is a viable starting point for a more durable data layer.
- GitHub Actions can trigger scheduled tasks independent of a sleeping web service.

### Structural issues

- The API composition root is a large, mixed-responsibility module; security policy and business logic are spread across route code and service methods.
- Runtime state is split between PostgreSQL and a set of JSON files. The JSON path is a hidden second production data architecture rather than a clearly scoped development adapter.
- Background work starts inside web-service startup and also has external cron triggers. There is no visible shared leader lock or globally durable job scheduler.
- ORM setup and schema changes happen on startup through `create_all` and manual alterations rather than a versioned migration system.
- There is no clear boundary between verified scholarship facts, search snippets, model-generated text, and user-supplied content in the product’s trust model.

### What breaks at increasing usage

These are reasoned failure modes, not load-test results.

| Concurrent/registered users | Likely behavior and bottlenecks |
|---|---|
| **100** | A demo may function, but email/Gemini provider quotas, duplicate background startup jobs, cold starts, and manual data curation become visible. JSON write contention can already lose updates under concurrent mutations. |
| **1,000** | Local rate limits and caches differ by process; account/notification writes can race across replicas; repeated search/AI calls consume quota; in-process work can compete with request handling. |
| **10,000** | The free-tier single web service is not a credible availability plan. The file fallback, per-process queue, lack of durable job coordination, limited observability, and inconsistent indexing make latency, duplicate emails, and data correctness failure likely. |
| **100,000** | The current architecture needs replacement in key areas, not just larger instances: API/service decomposition, normalized/indexed multi-tenant data, durable queues/workflows, shared cache/rate limits, object storage/CDN, ingestion/search infrastructure, SLOs, privacy operations, and a tested disaster-recovery strategy. |

## 6. Database and data review

### Current model

`services/db.py` defines SQLAlchemy models for users, subscribers, scholarships, notification history/events, community posts/comments/follows/reports/stories, news, and token revocation. The current repository also contains parallel JSON stores under `data/`.

### Risks and recommendations

1. **Sensitive JSON records are tracked.** See Security Finding 2. This must be resolved before further deployment.
2. **No relational foreign-key relationships were found in the ORM model declarations.** Most cross-entity references are string IDs/emails or JSON lists. That weakens referential integrity and makes deletes/ownership checks harder to enforce.
3. **JSON/array fields carry application relationships and profile lists.** This is flexible early on but limits constraints, querying, indexing, and analytics as user volume grows. Normalize relationships that need filtering, ownership, uniqueness, or reporting.
4. **Dates are represented as strings in several entities.** Use timezone-aware timestamps and typed date columns for deadlines, created/updated times, and notification delivery; define UTC handling at the API boundary.
5. **Indexes are selective.** User email/username and several notification recipient fields are indexed, and there is a composite unique sent-notification index. Add indexes from measured query plans for ownership plus status/time ordering and common scholarship filters. Avoid adding indexes without `EXPLAIN ANALYZE`.
6. **Schema evolution is startup code.** `Base.metadata.create_all` plus manual `ALTER TABLE` logic is not a migration history. Use Alembic (or an equivalent) with reviewed, ordered migrations and rollback/forward-compatibility procedures.
7. **Connection pool is per process.** The configured Postgres pool is size 2 with 5 overflow connections; deployment scaling multiplies this by workers/instances. Set a global connection budget against the database tier and expose pool saturation metrics.
8. **JSON fallback is not a safe production failover.** Atomic file replacement does not by itself provide cross-process transactions, conflict detection, or safe read-modify-write semantics. Do not silently switch production identity/business data to local files when Postgres is unreachable.
9. **Backups and data lifecycle are not established by code.** Define retention, account deletion propagation, export, backup encryption, restore drills, and privacy-request handling.

## 7. AI assistant review

### Current state

`AdvisorService` combines profile/context lookup, deterministic catalog responses, intent classification, similarity caching, and Gemini generation. `GeminiService` formats scholarship/search results for generation and can return a curated fallback. The system has prompt-sanitization helpers and includes instructions to treat search data as untrusted. That is a useful baseline, but not a world-class or production-grade scholarship advisor yet.

### Key gaps

- **Source freshness and provenance:** hard-coded opportunities/deadlines are called verified, but source records do not consistently expose a reviewer, official source, verified timestamp, expiry, or audit trail. Several curated deadlines were in the past on 22 November 2026.
- **Confidence calibration:** a numeric “chance” should not be presented as admission probability without historical outcomes, calibration, cohort definitions, and uncertainty bounds. Rename it to a transparent eligibility/readiness score until validated.
- **Personalization controls:** user profile and chat history are sensitive inputs. Enforce data minimization, consent, retention, deletion, and strict per-user cache scoping. The cache issue in Finding 1 is a release blocker.
- **Prompt injection / indirect instructions:** delimit and label retrieved material as untrusted data; do not let page text or user documents issue tool instructions. The current instruction is helpful but not a security boundary. Do not give the model authority to send messages, change accounts, or mutate records without server-side authorization and user confirmation.
- **RAG and attribution:** this code is not a mature RAG system with versioned document ingestion, chunk provenance, retrieval evaluation, citation validation, and stale-source invalidation. Require official citations beside every deadline/eligibility/funding claim and refuse unsupported details.
- **Evaluation:** no maintained golden test set, answer-quality rubric, citation accuracy metric, hallucination tracking, demographic/fairness evaluation, or prompt regression suite is evidenced.
- **Fallback behavior:** static fallback text can appear current even when deadlines are expired. Fallbacks must be marked with retrieval time and stale status; if no current evidence is available, say so rather than asserting eligibility or funding.
- **Cost/abuse controls:** rate limits and quotas must be shared across replicas and keyed by account/IP as appropriate; enforce token, document-size, and spend budgets at a gateway/service boundary.

### World-class advisor target

1. Build a canonical scholarship record with official source URL, captured evidence, normalized eligibility criteria, country/residency rules, dates/timezone, funding components, reviewer/verification status, `verified_at`, and `expires_at`.
2. Ingest from approved sources into a review queue; preserve source snapshots and diffs; revalidate before publishing and automatically expire stale records.
3. Use deterministic eligibility rules for hard requirements and show a criterion-by-criterion explanation. Keep model generation for coaching and summarization, not authoritative eligibility decisions.
4. Generate advice with citations to current, official evidence; validate that cited sources support claims and flag missing evidence.
5. Separate the user profile from the public scholarship context, minimize prompts, redact unnecessary identifiers, and give users explicit controls for history deletion and AI processing.
6. Add offline evaluation: eligibility precision/recall, deadline accuracy, citation precision, calibrated readiness scoring, multilingual quality, and fairness slices.
7. Present uncertainty honestly: “meets listed criteria” is different from “likely to win”; state unknowns and ask for missing details.
8. Provide actionable outputs: application checklist, deadline calendar, requirements gaps, draft history, reminders, and official portal links.

## 8. Product and market analysis

### Positioning and alternatives

| Alternative | Strength | EduAtlas opportunity | EduAtlas risk |
|---|---|---|---|
| Official scholarship portals/directories | Authoritative source and application route | Aggregate across funders and add personalized workflow | Must not replace or misstate official rules; freshness is essential. |
| General AI assistants | Flexible conversational help | Structured catalog, profile-aware filters, reminders, and application workspace | Generic generation is not reliable eligibility evidence or a calibrated admissions model. |

### Why a student might choose it

- One workflow for discovery, qualification, preparation, and deadline tracking.
- Clear relevance to international applicants and potential Arabic/English support.
- A combination of scholarship data, application tools, and student experiences.

### Weaknesses and missing differentiation

## 9. Deployment and operations review

- **Render:** `render.yaml` selects the free plan. Treat this as a demo/pilot setting; it does not establish high availability or predictable latency. Define production plan, autoscaling, maintenance, and recovery targets.
- **Startup work:** the app starts news/automation daemons during web startup. Every replica/restart can start another copy; there is no visible global scheduler lock. Move recurring work to a durable worker/scheduler with idempotent jobs and distributed locking.
- **GitHub cron:** the workflows provide useful triggers, but the global trigger script reports success if either of two operations succeeds; both operations should be independently checked and failures should fail the workflow. Add concurrency control, retries with bounds, alerting, and authenticated least-privilege secrets.
- **Container build:** `Dockerfile` copies the whole repository. `.dockerignore` does not exclude runtime JSON or uploads, and so the image can contain local data/media. Use an allowlist build context and separate persistent storage.
- **Environment:** secrets are correctly modeled as environment variables in Render configuration, but production values are not verifiable from source. Replace the wildcard `ALLOWED_ORIGINS` sample with an explicit allowlist and test the effective configuration rather than relying on fallback behavior.
- **Logging/monitoring:** standard logging exists, but no durable centralized log/metric/trace setup, SLOs, alert thresholds, error tracking, or structured request/job correlation was evidenced.
- **Background jobs:** a process-local notification worker and startup tasks cannot guarantee delivery across restarts or replicas. Add a durable queue, job leases, idempotency keys, dead-letter handling, and delivery reconciliation.
- **Dependency/build control:** pin Python resolution; run npm/Python audits and tests in CI. The npm audit found zero vulnerabilities in the current lockfile; Python auditing was blocked by the unavailable package resolution.
- **Health checks:** health routes exist, but readiness should distinguish database/queue/provider state and must not silently report a healthy app when critical persistence is degraded.

## 12. Transforming the project into a global scholarship platform

The global-scale path is not “add more prompts and run more replicas.” It is to turn the scholarship dataset and application workflow into a trusted, auditable product:

1. **Make trust the moat.** Use canonical opportunity records, official evidence snapshots, transparent country-specific eligibility, freshness indicators, and reviewer accountability.
2. **Separate source facts from generated advice.** Deterministic rules decide whether listed criteria are met; AI explains, plans, translates, and drafts with citations. It must not invent deadlines, guarantees, or acceptance odds.
3. **Build the student workflow.** A student should be able to go from profile → eligible opportunities → requirements gaps → documents → submissions → deadline reminders → outcomes.
4. **Design for privacy.** Keep account and document data out of Git/images, minimize provider disclosures, provide export/deletion/retention controls, and isolate every user-owned record and cache entry.
5. **Use a scalable service foundation.** Stateless web/API replicas; managed, normalized PostgreSQL with versioned migrations; shared Redis for rate limits/cache; durable job queue; private object storage; CDN; and separate ingestion workers.
6. **Operate the data pipeline.** Track provider/source, retrieval timestamp, evidence, reviewer, change history, expiration, and correction workflows. Add monitoring for stale or conflicting facts.
7. **Measure outcomes and quality.** Track source accuracy, match explainability, citation correctness, application completion, fairness, and user-reported outcomes—not just chatbot response count.
8. **Grow by verified markets.** Launch one or two student segments first, localize credential equivalencies and application guidance, then expand through universities, governments, foundations, and vetted scholarship providers.
9. **Create sustainable distribution and economics.** Build counselor/partner channels and transparent paid tools for organizations; keep student access affordable and do not sell personal data or paid ranking.
10. **Treat operations as product.** Set SLOs, incident response, abuse/moderation procedures, customer support, privacy/legal review, backup/restore drills, and capacity planning before scaling to hundreds of thousands.

**Bottom line:** EduAtlas has a compelling product direction and substantial prototype work, but global readiness depends on verified data, privacy-by-design, durable persistence/jobs, measured AI quality, and operational discipline. Resolve the P0 issues and establish a trustworthy, narrow MVP before accelerating feature development.
